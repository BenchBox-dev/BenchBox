# Agent attribution on published surfaces

`[COMMIT-IDENTITY-001]` in `AGENTS.md` is the authority. This note records the
mechanism it is reacting to and the trade-off accepted, so the decision is not
re-litigated from scratch.

## What was observed

Agent-authored GitHub posts arrived carrying a trailing rule and an italic
attribution line. A live instance is the closing comment on PR #1494
(`issue_comment` 5174430128), which ends with a `---` rule followed by
`_Generated by [Claude Code](https://claude.ai/code)_`.

Two details make it more than cosmetic:

- **It posts as the repository owner.** That comment's `user.login` is
  `joeharris76` with `author_association: OWNER`. The footer therefore renders
  as the maintainer announcing that their own comment was machine-generated.
- **The strings diverge by surface.** Comments carry
  `Generated by [Claude Code](https://claude.ai/code)`; pull request bodies
  carry `Generated with [Claude Code](https://claude.com/claude-code)` plus a
  session URL. PR #1494's description and its comment did not match.

## Origin

The footers are appended by the agent harness's own operating instructions,
which direct the agent to end every comment, review, review reply, and issue
comment with the attribution footer, and to include it even when the posting
tool would add one (duplicates are stripped server-side). A separate
instruction covers pull request bodies with the differently-worded variant.

This is the same class as the agent `Co-Authored-By` commit trailer: external in
origin, applied by convention rather than by request. `AGENTS.md` already
answers that class — a tool convention is not authorization.

## Why the rule is advisory, not enforced

The commit trailer is catchable because a commit passes through
`.git/hooks/commit-msg`, where `scripts/check_agent_trailers.sh` rejects it. A
GitHub comment has no equivalent chokepoint: the agent calls the GitHub API
directly, and no repository-side control sits in that path. Any mechanical
check here is necessarily after the fact — a workflow that reads posted
comments and flags the footer, which detects rather than prevents. That is a
real option, but it should not be described as prevention.

## The trade-off accepted

Suppressing the footer removes the only standing signal that separates an
agent-authored comment from a human one on an OWNER-attributed post. That cost
is accepted deliberately, on two grounds: a footer on every post is noise that
readers stop seeing, and a blanket machine marker under the maintainer's account
is itself misleading about who is speaking. The rule therefore asks for
disclosure **in the text, where it is load-bearing** — for example when a
comment reports what an agent verified, or when a reviewer would act differently
knowing the analysis was automated — instead of an unconditional footer.

Two alternatives were considered and not chosen:

- **Unify the two footers into one shorter string.** Keeps a disclosure signal
  and fixes the surface-dependent inconsistency, but retains a standing marker
  under the owner's account.
- **Post agent comments from a bot identity.** The strongest option, because
  attribution becomes implicit in the account rather than appended to the body.
  It needs a bot account and token provisioning, so it is out of scope here; if
  that ever lands, this rule should be revisited, since the footer's job would
  then be done by the account itself.
