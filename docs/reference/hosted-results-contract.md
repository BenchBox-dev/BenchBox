# Hosted Results Contract and Governance Model

**Created:** 2026-04-01
**Originating TODO:** `define-hosted-results-contract-and-governance-model`
**Authoritative foundation:** `docs/development/benchbox-results-platform-strategy.md`

## Overview

This document defines the identity model, visibility states, trust labels, cohort
eligibility rules, privacy policy, and consumer contracts for the BenchBox hosted
results platform. It covers all three rollout phases:

- **Phase 1** - Static explorer MVP. All results are maintainer-curated. No
  community submissions, no auth, no hosted API.
- **Phase 2** - PR-based community contributions. Community submitters open pull
  requests against `results-data/`; GitHub Actions validates; maintainers merge.
- **Phase 3** - Hosted API with auth, rate limiting, and self-service submission.
  Only built if Phase 2 PR volume exceeds maintainer capacity.

Consumers of this contract: the `benchbox submit` CLI command, the hosted API
(Phase 3), and the results explorer frontend. Each section concludes with a
phase annotation indicating when the rules apply.

## 1. Result Identity Model

### 1.1 Identifiers

Three distinct identifiers exist for every result entry. They serve different
purposes and have different lifetimes.

#### `bundle_hash`

A SHA-256 digest of the raw canonical schema-v2 bundle JSON bytes, computed
before any normalization or storage transformation.

| Property | Value |
|---|---|
| Computation | `sha256(raw_bundle_bytes)` - bytes as written by `benchbox run` |
| Stability | Immutable. The hash changes only if the bundle contents change. |
| Uniqueness | Content-addressable. Two identical runs produce the same hash. |
| Phase introduced | Phase 2 (PR CI validation); formally tracked from Phase 3 |
| Used for | Deduplication, integrity verification, idempotent re-upload detection |

The `bundle_hash` is included in the submission manifest that `benchbox submit`
packages alongside the bundle. CI uses it to detect re-submitted identical bundles.

#### `submission_id`

A server-generated UUID (v4) assigned at first ingest of a bundle.

| Property | Value |
|---|---|
| Computation | Generated by ingest service on first receipt |
| Stability | Stable across re-uploads of the same bundle (same `bundle_hash` → same `submission_id`) |
| Uniqueness | Unique per distinct bundle content (deterministically derived from `bundle_hash`) |
| Phase introduced | Phase 3 (Phase 2 uses the PR number as a submission handle) |
| Used for | API responses, status polling, audit trail |

Re-uploading a bundle with a known `bundle_hash` returns the existing
`submission_id` rather than creating a new one. This makes the ingest endpoint
idempotent with respect to content.

#### `public_result_id`

A stable, human-readable permalink slug that identifies a result in the public
corpus.

| Property | Value |
|---|---|
| Format | `{benchmark}-{platform}-sf{scale_factor}-{date}` (e.g., `tpch-duckdb-sf1-20260315`) |
| Stability | Permanent once minted. Never reused for a different result. |
| Uniqueness | Unique within the public corpus. Conflicts are resolved by the minting service (not the submitter) appending `-{n}`, where `n` starts at 2 and increments monotonically (e.g., `-2`, `-3`). |
| Minting | Phase 1: on commit to `results-data/`. Phase 2+: after validation passes. |
| Phase introduced | Phase 1 |
| Used for | Stable URLs (`/results/r/{public_result_id}`), manifest index, compare links |

The `public_result_id` is the only identifier that is stable across all phases
and safe to use in external links. CLI tools and frontend must use this identifier
for any URL or reference intended to be shared or bookmarked.

#### Identifier Summary

| Identifier | Stability | Phase | Purpose |
|---|---|---|---|
| `bundle_hash` | Content hash, immutable | 2+ | Dedup, integrity |
| `submission_id` | UUID, stable per bundle | 3 | API tracking |
| `public_result_id` | Slug, permanent | 1+ | Public URLs, index |

### 1.2 Ingest Status Model

Every submitted result moves through a defined set of statuses. The status
determines whether the result appears in the public corpus and what actions are
available.

#### Status Definitions

| Status | Meaning | Visible to public |
|---|---|---|
| `pending` | Received; awaiting validation | No |
| `validated` | Passed all automated checks; awaiting publication decision | No |
| `published` | Live in the public corpus with a `public_result_id` | Yes |
| `rejected` | Failed validation or declined by maintainer; includes a reason string | No |
| `withdrawn` | Removed from public index at submitter or admin request | No (tombstone only) |

#### Status Transition Rules

```
pending → validated → published
pending → rejected
validated → rejected
published → withdrawn
```

Transitions are unidirectional. A `rejected` or `withdrawn` result cannot be
re-promoted; the submitter must open a new submission.

Additional rules:

- **Idempotent re-upload:** Submitting a bundle whose `bundle_hash` already maps
  to a `published` result returns the existing `public_result_id` and a
  `200 OK` response with `"status": "already_published"` in the body. No new
  `submission_id` is created.
- **Rejection reason:** Every `rejected` transition must carry a human-readable
  `reason` string. Reasons are visible to the submitter but not to the public.
- **Withdrawn tombstone:** In Phases 1-2, withdrawal removes the entry entirely
  from the index (no tombstone is retained). In Phase 3, a `withdrawn` result
  retains its `public_result_id` in the index as a tombstone stub with all
  content fields redacted. See Section 4.4.

#### Phase Assignment

| Status | Phase 1 | Phase 2 | Phase 3 |
|---|---|---|---|
| `pending` | Not used (no ingest) | PR open, CI running | API received |
| `validated` | Not used | CI passed, awaiting merge | Async validation passed |
| `published` | On commit to `results-data/` | On PR merge | On promotion |
| `rejected` | Not used | CI failed or PR closed without merge | Validation failed |
| `withdrawn` | Admin removes from `results-data/` | Same | API call or admin action |

## 2. Visibility States and Trust Labels

### 2.1 Visibility States

Five visibility states control who can see a result and whether it appears in
search indexes or compare views.

| State | Who can see it | Indexed | Phase available |
|---|---|---|---|
| `private` | Submitter only | No | Phase 3 |
| `unlisted` | Anyone with the direct URL | No | Phase 3 |
| `public-self-reported` | Everyone | Yes | Phase 2+ |
| `public-curated` | Everyone | Yes | Phase 1+ |
| `public-verified` | Everyone | Yes | Future (reserved) |

**`private`** - The result bundle is stored but the `public_result_id` is not
minted. Useful for submitters who want to validate their results before
publishing. Not available in Phase 1 or Phase 2 (no auth layer exists).

**`unlisted`** - The `public_result_id` is minted and the detail page is
accessible, but the result does not appear in the manifest index, search
results, or compare view browse. Useful for sharing a single result with a
specific audience. Not available before Phase 3.

**`public-self-reported`** - Fully public and indexed. Results submitted via
community PR (Phase 2) or self-service API (Phase 3) start in this state.
The result carries a "Self-Reported" label (see Section 2.2).

**`public-curated`** - Fully public and indexed. Results generated and
committed by BenchBox maintainers carry this visibility. This is the only
state available in Phase 1.

**`public-verified`** - Reserved for future third-party attestation workflows.
No results carry this state at launch; the attestation mechanics are not yet defined.

### 2.2 Trust Labels

Trust labels communicate the provenance and review depth of a result to
explorer visitors. Labels appear on result detail pages, compare view headers,
and manifest index cards.

| Label | Display text | Visibility state | Meaning |
|---|---|---|---|
| `maintainer-run` | "Maintainer Run" | `public-curated` | Run by BenchBox maintainers in a controlled environment |
| `community-submission` | "Community Submission" | `public-self-reported` | Submitted by a community contributor via PR or API |
| `verified` | "Verified" | `public-verified` | Attested by a third party (reserved, not yet in use) |

Trust labels are informational. They do not imply that one result is more
accurate than another; they communicate who ran the benchmark and under what
level of review.

### 2.3 Phase-by-Phase Display Rules

#### Phase 1

All results carry the `public-curated` visibility state and the `maintainer-run`
trust label. No label selection logic is needed; the label is hardcoded in the
static build pipeline.

#### Phase 2

Results fall into one of two categories based on their submission path:

| Submission path | Visibility state | Trust label |
|---|---|---|
| Committed by maintainer CI | `public-curated` | Maintainer Run |
| Merged from community PR | `public-self-reported` | Community Submission |

The explorer renders both labels. A legend on the browse and compare pages
explains the distinction.

#### Phase 3

All five visibility states apply. The full label spectrum is rendered. The
explorer must handle the case where a compare view contains results with
different trust labels and display a per-result label badge rather than a
single cohort-level label.

## 3. Cohort Eligibility and Ranking Rules

### 3.1 Comparison Cohort Definition

A valid comparison cohort is a set of results that can be meaningfully compared
side-by-side in the explore compare view.

**Required for a valid cohort:**

| Field | Requirement |
|---|---|
| `benchmark` | Must be identical across all results in the cohort (e.g., `tpch`) |
| `scale_factor` | Must be identical across all results in the cohort (e.g., `1.0`) |

These two fields form the minimum cohort key. Results with different values on
either field cannot appear in the same compare view.

### 3.2 Hard Blocks

The following mismatches are hard blocks. The compare view refuses to render
and returns an error message explaining why the comparison is invalid.

| Mismatch | Error message shown |
|---|---|
| Different `benchmark` | "Cannot compare results from different benchmarks. Select results from the same benchmark." |
| Different `scale_factor` | "Cannot compare results at different scale factors. Select results at the same scale factor." |

Hard blocks apply in all phases. There is no override mechanism. The frontend
must enforce this check client-side before attempting to render a comparison;
the API (Phase 3) must enforce it server-side as well.

### 3.3 Soft Warnings

The following mismatches are soft warnings. The compare view renders but
displays a prominent inline warning banner explaining which fields differ and
how that may affect interpretation.

| Mismatch | Warning message |
|---|---|
| Different `query_subset` | "Warning: these results use different query subsets. Totals and rankings reflect different query sets and may not be directly comparable." |
| Different `tuning_mode` | "Warning: these results use different tuning modes (`tuned` vs `notuning`). Performance differences may reflect tuning rather than platform capability." |

Soft warnings do not prevent rendering. The compare view shows all selected
results with the warning banner at the top. Users may dismiss the warning after
reading it.

Additional fields that produce soft warnings if they differ: `phases` (e.g.,
comparing a power-only run against a throughput+power run), `driver_version`
(if the submitter has pinned a non-default driver version).

### 3.4 Ranking Eligibility

Not all results are eligible for inclusion in ranked tables or aggregate
leaderboard views within a cohort.

| Visibility state | Eligible for ranked tables |
|---|---|
| `public-curated` | Yes |
| `public-verified` | Yes (reserved) |
| `public-self-reported` | No |
| `unlisted` | No |
| `private` | No |

`public-self-reported` results appear in browse views and can be selected for
pairwise comparison, but they are excluded from any sorted table that is
presented as a ranking. This prevents unverified results from affecting the
official leaderboard within a cohort.

Ranking totals and cohort-relative speedups count only ranking-eligible rows
with non-null primary metrics. Visible rows that are not eligible keep their
raw metrics for browse and comparison surfaces, but carry `rank = null` and do
not define the cohort's best or slowest ranked value.

The explorer must not display a ranked table that mixes `public-curated` and
`public-self-reported` results without clear visual separation. If a cohort
contains only `public-self-reported` results, the view renders as a browse list,
not a ranked table.

## 4. Privacy, Redaction, and Retention

### 4.1 Public Fields

The following fields are always public for any result with a `published` status
and a public visibility state. They cannot be redacted by the submitter or
admin.

| Field | Notes |
|---|---|
| `benchmark` | Benchmark family (e.g., `tpch`) |
| `platform` | Platform identifier (e.g., `duckdb`) |
| `scale_factor` | Numeric scale factor (e.g., `1.0`) |
| `query_timings` | Per-query execution time in milliseconds |
| `validation_status` | Per-query validation result (passed/failed/skipped) |
| `submission_date` | Date the result was published to the corpus |
| `trust_label` | The trust label assigned at publication |
| `public_result_id` | The stable permalink slug |
| `query_subset` | Which queries were run (full set or named subset) |
| `tuning_mode` | Whether platform tuning was applied |

### 4.2 Redactable Fields

The following fields may be redacted by the submitter before submission or
requested for redaction after publication. Admins may also redact any field.
Redacted fields are replaced with the sentinel value `"[redacted]"` in all
public-facing views.

| Field | Who may redact | Notes |
|---|---|---|
| `system_hostname` | Submitter or admin | The machine name where the benchmark ran |
| `os_version` | Submitter or admin | Exact OS version string (e.g., `Ubuntu 22.04.3 LTS`) |
| `private_config_values` | Submitter or admin | Any platform-option key=value pairs the submitter marks private |
| `contributor_email` | Submitter or admin | Only collected in Phase 3; display name is shown instead |
| `ip_address` | Admin only (never public) | Stored for abuse detection; never exposed |

Redaction of a published field does not change the result's `published` status
or `public_result_id`. The result remains in the public index; only the
specific field value is hidden.

### 4.3 Retention Policy

| Status | Retention |
|---|---|
| `published` | Retained indefinitely by default. No automatic expiry. |
| `pending` / `validated` | Retained for 90 days from submission date, then purged if not promoted. |
| `rejected` | Retained for 30 days from rejection date, then purged. |
| `withdrawn` | Public index tombstone retained indefinitely. Raw bundle purged within 30 days of withdrawal. |

The indefinite retention of `published` results is the default. Submitters may
request withdrawal at any time (see Section 4.4); the platform does not
proactively expire published results.

### 4.4 Data Removal

Submitters may request withdrawal of a published result at any time. There is
no deadline. Withdrawal is available before and after publication.

**Withdrawal process:**

- Phase 1: File an issue or contact maintainers. The maintainer removes the
  bundle from `results-data/` and triggers a rebuild.
- Phase 2: Same as Phase 1, or close the original PR (if not yet merged).
- Phase 3: Call `DELETE /v1/results/{public_result_id}` with a valid auth token,
  or contact support.

**Effect of withdrawal:**

1. The result is removed from the public manifest index and all browse/compare
   views within 7 days of the withdrawal request.
2. The raw bundle and all derived read models are purged from storage within
   30 days of the withdrawal request.
3. **Phase 3 only:** A **tombstone** remains in the index indefinitely. The
   tombstone contains only: `public_result_id`, `status: withdrawn`, and
   `withdrawn_at` (date). All other fields are redacted. The detail page at
   the stable URL returns the tombstone with a `410 Gone` HTTP status.
   In Phases 1-2, withdrawal removes the entry entirely from the index; no
   tombstone is retained (the stable URL returns `404 Not Found`).

In Phase 3, the tombstone ensures that existing links and citations do not
silently resolve to a different result. External parties who bookmarked the URL
see a clear signal that the result was withdrawn rather than a 404 or an
unrelated result.

## 5. Consumer Contract Reference

### 5.1 CLI Contract

The `benchbox submit` command is the primary submission interface for Phase 2
and Phase 3. This section defines what the CLI must do and what it can expect
in return.

#### What `benchbox submit` packages

The CLI packages a **submission bundle** consisting of:

| Component | Description |
|---|---|
| Canonical schema-v2 bundle | The `.json` file produced by `benchbox run`, unmodified |
| Companion files | Any files referenced in the bundle (query plans, etc.), if present |
| Submission manifest | A `submission.json` sidecar with contributor metadata |

#### Result bundle schema policy

The canonical bundle is schema-v2 JSON. The current BenchBox producer writes
top-level `"version": "2.1"`. Public PR submission validation accepts numeric
schema version family `2.x` so a future producer minor can be submitted before
the hosted contract document is updated, but it rejects missing or malformed
versions.

Downstream consumers are stricter than public ingest:

| Consumer | Accepted versions | Failure behavior |
|---|---|---|
| Runtime loader | `"2.0"`, `"2.1"` | Rejects with the runtime loader schema policy and asks for re-export. |
| Explorer static pipeline | `"2.0"`, `"2.1"` | Rejects before manifest/detail projection to avoid silent field drops. |
| Normalizer | `"2.0"`, `"2.1"` as v2; other shapes as legacy | Uses best-effort legacy extraction for v1.x and unknown shapes. |

Any change to accepted versions or field semantics must update
`benchbox.core.results.schema_policy`, this contract, and the public contract
map in the same PR.

The submission manifest schema:

```json
{
  "submission_tool_version": "<'benchbox/' + semver string>",
  "submitted_at": "<ISO 8601 UTC timestamp>",
  "bundle_file": "<filename of primary result JSON>",
  "bundle_hash": "<sha256 of primary result JSON>",
  "companion_hashes": {
    "<companion filename>": "<sha256 of companion file>"
  },
  "benchmark": "<benchmark name from result>",
  "platform": "<platform name from result>",
  "scale_factor": "<scale factor from result>",
  "phase": 2,
  "submission_path": "PR-based",
  "submitted_by": "<GitHub username or display name - Phase 2: PR author; Phase 3: authenticated actor>",
  "submission_notes": "<optional free-text, max 500 chars>"
}
```

**Field notes:**
- `submitted_by`, `submission_notes`: Phase 2 - optional; Phase 3 - required.
- `benchmark`, `platform`, `scale_factor`, `bundle_file`, `phase`, `submission_path`: All phases - required, extracted from result metadata.

#### `bundle_hash` computation

The CLI computes `bundle_hash` as the SHA-256 of the primary result JSON bytes.
Companion files are covered separately through `companion_hashes`, a mapping of
companion filename to SHA-256. The manifest itself is excluded because it is
created after these hashes are computed. Hashes must be recomputed at submission
time, not cached from a prior run, to detect post-run modifications.

#### Dry-run behavior

When invoked with `--dry-run`, `benchbox submit`:

1. Computes `bundle_hash` and validates it against the bundle contents.
2. Runs all client-side cohort and schema validations.
3. Prints a summary of what would be submitted (benchmark, platform, scale,
   hash, estimated submission manifest).
4. Does NOT write to `results-data/`, open a PR, or contact the API.
5. Exits with code 0 if validation passes, non-zero if it fails.

Dry-run is the recommended way to verify a submission before committing.

#### Phase 2 output mode (`--output`)

`benchbox submit --output ./submission/` writes the submission bundle to a
local directory for manual PR submission. No network calls are made. The
output directory contains:

```
submission/
  bundle/
    <result_filename>.json
    <result_filename>.plans.json   (if present)
    <result_filename>.tuning.json  (if present)
  <result_filename>.manifest.json
  CONTRIBUTING.md
```

The contributor opens a PR against `published-results` by copying the contents
of `bundle/` into `results-data/bundles/` and placing
`<result_filename>.manifest.json` alongside the bundle files. See
`CONTRIBUTING.md` in the output directory for step-by-step instructions.

#### Phase 3 API mode

When `--service [URL]` is passed, the CLI POSTs the submission bundle directly
to the hosted API. Authentication comes from `benchbox auth login` keyring
storage, `BENCHBOX_SUBMIT_TOKEN`, or the lower-precedence
`BENCHBOX_SERVICE_TOKEN`; dry runs do not require credentials.

```
POST /v1/submissions
Content-Type: multipart/form-data

bundle:       <bundle.json bytes>
manifest:     <submission.json bytes>
companions[]: <companion files, if any>
```

Expected responses:

| HTTP status | Meaning | CLI behavior |
|---|---|---|
| `202 Accepted` | Submission received; `submission_id` in body | Print submission_id and poll URL |
| `200 OK` | `bundle_hash` already published; body includes `"status": "already_published"` and `public_result_id` | Print existing result URL, exit 0 |
| `409 Conflict` | Bundle in `pending` or `validated` state; `submission_id` in body | Print status and poll URL |
| `422 Unprocessable` | Schema or hash validation failed; `errors` array in body | Print errors, exit non-zero |
| `429 Too Many Requests` | Rate limited; `Retry-After` in headers | Print wait time, exit non-zero |

#### Status polling contract

After a Phase 3 submission, the CLI may poll for status:

```
GET /v1/submissions/{submission_id}/status
```

Response:

```json
{
  "submission_id": "<uuid>",
  "bundle_hash": "<sha256>",
  "status": "<pending|validated|published|rejected>",
  "public_result_id": "<slug or null>",
  "rejection_reason": "<string or null>",
  "updated_at": "<ISO 8601>"
}
```

The CLI polls with exponential backoff (initial 5s, max 60s, up to 10 attempts)
and prints the final status to stdout.

### 5.2 API Contract (Phase 3)

The hosted API is available at `api.benchbox.dev`.

#### Endpoint surface

| Method | Path | Auth required | Description |
|---|---|---|---|
| `POST` | `/v1/submissions` | Yes | Submit a new bundle |
| `GET` | `/v1/submissions/{submission_id}/status` | Yes | Poll submission status |
| `GET` | `/v1/results` | No | List published results (paginated) |
| `GET` | `/v1/results/{public_result_id}` | No | Get result detail |
| `DELETE` | `/v1/results/{public_result_id}` | Yes (owner or admin) | Withdraw a result |
| `GET` | `/v1/cohorts` | No | List available cohorts (benchmark + scale combinations) |
| `GET` | `/v1/compare` | No | Compare results by IDs (cohort validation enforced) |

All public read endpoints (`GET /v1/results`, `GET /v1/results/{id}`,
`GET /v1/cohorts`, `GET /v1/compare`) are unauthenticated. Rate limits apply
to all endpoints; authenticated requests receive higher limits.

#### Response envelope

All API responses use a consistent envelope:

```json
{
  "data": { ... },
  "error": null,
  "meta": {
    "request_id": "<uuid>",
    "timestamp": "<ISO 8601>"
  }
}
```

Error responses set `data: null` and populate `error`:

```json
{
  "data": null,
  "error": {
    "code": "VALIDATION_FAILED",
    "message": "bundle_hash mismatch",
    "details": [ ... ]
  },
  "meta": { ... }
}
```

#### Rate limits

| Endpoint group | Unauthenticated | Authenticated |
|---|---|---|
| Read endpoints | 60 req/min | 600 req/min |
| Submission endpoints | Not available | 10 req/min |
| Status polling | Not available | 120 req/min |

Rate limit headers are returned on every response:
`X-RateLimit-Limit`, `X-RateLimit-Remaining`, `X-RateLimit-Reset`.

### 5.3 Frontend/Explorer Contract

The explorer frontend consumes the static manifest JSON and the DuckDB database
file. In Phase 3 it may also call the read API. This section defines what the
frontend must know about visibility, trust, cohorts, and redaction.

#### Visibility state rendering

| Visibility state | Render in browse index | Render in compare | Show detail page |
|---|---|---|---|
| `private` | No | No | No (404) |
| `unlisted` | No | No | Yes (direct URL only) |
| `public-self-reported` | Yes | Yes | Yes |
| `public-curated` | Yes | Yes | Yes |
| `public-verified` | Yes | Yes | Yes |

The frontend must not expose `private` or `unlisted` results in any index or
search view. For `unlisted`, the detail page is accessible if the user has the
direct URL, but the result must not appear in autocomplete, search, or browse.

#### Trust label rendering rules

- Every result card, detail page header, and compare view row must display the
  trust label badge.
- In a compare view containing results with different trust labels, each result
  row displays its own badge. No aggregate or cohort-level badge is shown.
- The badge for `public-curated` is rendered in the primary brand color.
- The badge for `public-self-reported` is rendered in a neutral/muted color.
- The `verified` badge (reserved) is rendered in a distinct accent color when
  implemented.
- A legend explaining all trust labels is accessible from every page that
  displays them (persistent tooltip or a "What does this mean?" link).

#### Cohort validation rules for compare view

The frontend enforces cohort rules before rendering:

1. **Hard block check:** If any two selected results differ in `benchmark` or
   `scale_factor`, show an error and refuse to render the comparison. Link to
   the result detail pages so the user can verify their selection.
2. **Soft warning check:** If any two selected results differ in `query_subset`
   or `tuning_mode`, show a dismissible warning banner above the comparison
   table. Do not block rendering.
3. **Ranking eligibility check:** If the cohort contains any `public-self-reported`
   results, render the table as a browse-style list (no rank column, no
   "ranking" label). If all results are `public-curated` or `public-verified`,
   a rank column and total-duration sort are permitted.

#### Privacy and redaction rendering

- Redacted fields display the sentinel string `"[redacted]"` in the UI, styled
  in a muted color (e.g., gray italic text). They are not hidden entirely.
- The detail page must not display fields that are absent from the result JSON
  (some results omit optional fields entirely; this is distinct from redaction).
- Withdrawn results (tombstone) render a dedicated "Result Withdrawn" page at
  the stable URL with the tombstone data and a brief explanation. HTTP 410 is
  returned for API consumers; the frontend shows a human-readable message.

### Open Questions (Phase 3)

The following questions are explicitly deferred to Phase 3 design and are not
resolved by this contract:

- **`public_result_id` collision resolution:** Algorithm and concurrency strategy
  when two submissions produce the same deterministic ID.
- **Idempotency semantics:** Re-submitting a bundle that is already in
  `pending` or `validated` state - return `200 OK` or `409 Conflict`?
- **Cross-visibility cohort comparisons:** Whether results in different
  visibility states (e.g., `private` and `public-curated`) may be included in
  the same compare cohort.
- **Withdrawn result URL behavior (Phases 1-2):** Return `404 Not Found` or a
  dedicated "result withdrawn" page at the stable URL.
- **Private result access control model:** Submitter-only access, or
  organisation-based sharing (e.g., all members of the submitter's GitHub org)?
- **Ranking eligibility rules for mixed-visibility cohorts:** Whether a cohort
  containing both `public-self-reported` and `public-curated` results is
  eligible for ranked display, and which rules govern it.
